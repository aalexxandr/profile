# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Package manager is `pnpm` (Node 24, see `.nvmrc`). Tests: Vitest + React Testing Library (happy-dom), colocated as `src/**/*.test.ts(x)`; `pnpm test` (one run) / `pnpm test:watch` / `pnpm test:coverage` (V8 coverage with global thresholds in `vitest.config.mts`, HTML report in `coverage/`; CI runs this instead of plain `test`, so raise thresholds as coverage grows and never lower them to make a build pass). E2E: Playwright in `e2e/` (desktop + mobile Chromium), `pnpm test:e2e` builds the app and serves it with the standalone server (`exec node .next/standalone/server.js` after `scripts/prepare-standalone.ts`, never `next start`: it does not work with `output: "standalone"`) on port 3100 itself; every Playwright web server is started as a direct process (`exec ...`, no `pnpm` wrapper) with `gracefulShutdown` SIGTERM, otherwise teardown hangs until `globalTimeout` and leaves orphans; it is not part of `check`, run it after routing/UI/proxy changes (needs `pnpm exec playwright install chromium` once). `?svgr` imports are stubbed in `vitest.config.mts`.

- `pnpm dev` — dev server; `pnpm build` / `pnpm start` — production build / serve
- `pnpm lint` (`lint:fix` to autofix), `pnpm format:check` (`format` to write), `pnpm typecheck` (`next typegen` + `tsc --noEmit`; typegen creates the gitignored `next-env.d.ts` that CI lacks)
- `pnpm check` — lint + format:check + typecheck + test + build (plain `test`, no coverage) (run before finishing a change)
- `pnpm api:generate` — reads the backend OpenAPI document (`$API_URL/docs-json`, default `http://localhost:3000`) and writes the types straight to `src/shared/api/generated/schema.d.ts` (the committed file is the contract snapshot; logic in `scripts/generate-api.mts`). Run it before using new backend fields; it fails with a short message without touching the file if the backend is unreachable. TODO (after the backend is deployed): add `api:check` (regenerate and fail on a diff vs. the committed `schema.d.ts`) to CI.
- `pnpm fsd:check` — Steiger FSD lint. It may fail with `EMFILE: too many open files, watch`; report that as an environment blocker, not a pass.

## Automation

- `.claude/settings.json` hooks: after every Edit/Write the file is formatted (Prettier) and fixed (ESLint) by `.claude/hooks/format-file.ts`; remaining ESLint errors are returned to you, fix them. On Stop, `typecheck` must pass (`.claude/hooks/typecheck-on-stop.ts`).
- Pre-commit (husky + lint-staged) runs ESLint/Prettier on staged files. CI (`.github/workflows/ci.yml`) runs lint, format:check, typecheck, test, build, fsd:check and e2e; the job and the Playwright install/e2e steps have `timeout-minutes`, Playwright has `timeout`/`expect.timeout`/CI-only `globalTimeout`, browser install goes through `scripts/retry.sh` with a cache, same-ref runs are cancelled (`concurrency`), and CI prints the `list` reporter so a stalled run shows its unfinished tests. `scripts/ci-config.test.ts` guards these limits: do not remove them.
- Reading secret env files (`.env`, `.env.local`, `.env.{development,production,test}[.local]`) is denied in `.claude/settings.json`; `.env.example` is readable and lists the variables.

## Next.js version warning

This is Next.js 16 (React 19, Tailwind 4) with breaking changes vs. older versions. Read the relevant guide in `node_modules/next/dist/docs/` before writing Next.js code. For example, the middleware file is `src/proxy.ts` exporting `proxy` (not `middleware`).

## Architecture

- FSD-like layout in `src/`: `app` → `views` → `widgets` → `shared`. (Next's `app/` is the FSD app layer; pages live in `views/` (`cases`, `case-details`, `contacts`, `home`) and are composed by thin route files in `src/app`.) Use the `feature-sliced-design` skill for any placement/import/public-API decision.
- Imports use the `@/` alias (e.g. `@/shared/i18n`); deep `../../` imports are an ESLint error.
- **i18n routing**: all routes live under `src/app/[locale]/` (locales `ru`, `en`; config in `src/shared/i18n`): `/`, `/cases`, `/cases/[slug]` (case details; slugs and data come from the backend, listed in the sitemap), `/contacts`. `src/proxy.ts` redirects unlocalized paths using the `Accept-Language` header. Server-only dictionary loading, metadata helpers and locale validation are in `src/shared/i18n-server` (dictionaries in `dictionaries/ru.ts` and `en.ts`).
- Every user-facing string, alt text, nav label and metadata goes through the dictionaries: add keys to the `Dictionary` type and to **both** `ru` and `en` (both are `satisfies Dictionary`, so `typecheck` catches mismatches).
- **Static fallback (TEMPORARY)**: when `API_URL` is unset, `getCases` / `getCase` serve `src/shared/content/cases.ts` (copied from the backend: shared fields once, texts per locale; public API `getCaseList`, `findCase`; unknown slug raises `ApiError(404)` like the backend) and send no request, so `pnpm build` needs no backend. With `API_URL` set they call the backend as before, so returning to the API is just setting `API_URL` for the build/deploy; afterwards delete `src/shared/content` and the two `if (!process.env.API_URL)` branches. E2E/CI keep using the stub backend (API mode).
- **Backend API**: the backend is the source of truth for case data. `src/shared/api` holds the generated types (`generated/`, never edit by hand) and a thin GET-only client on `openapi-fetch`: `error.ts` (`ApiError`), `client.ts` (`createApiClient` from `API_URL`, `unwrap`), exported with the `Schemas` type from `@/shared/api`. The list and the case page are two independent slices: `src/views/cases` (list: `getCases(locale)`, `CaseListItem`, `CasesPage`) and `src/views/case-details` (`getCase(slug, locale)` wrapped in `React.cache`, `CaseDetail`, `CaseDetailPage`, `createCaseMetadata`); move a request to `shared/api` only when a second slice needs it. It is server-only and reads the server-only `API_URL` variable (no `NEXT_PUBLIC_`, listed in `.env.example`); admin operations are not exposed. Dates arrive as strings. The cases pages are pure SSG: `generateStaticParams` and the sitemap read the slugs from the backend, so **`pnpm build` needs a reachable backend** (a failing request fails the build; there is no ISR/`revalidate`, content changes appear after a rebuild). Unknown slugs are 404 (`dynamicParams = false`). The case detail type also carries nullable `backgroundImage` / `backgroundBlurImage` (the list item does not); they are the header background of the case page (dark `canvas` when `null`, no `noImage` text). The case page (`CaseDetailPage`, no `RetroWindow`) is composed of `CaseHeader` (a folder: `CaseBackground`, `CaseBackLink`, `CaseFacts`; the facts, their order and the null rules come from `lib/getCaseFacts`, the formatting from `lib/formatPeriod` and `lib/formatTeamSize`), `CaseAbout` (description and project link), `CaseStack` (technologies in a row, framed with `public/code-border.png`) and `CaseAchievements` (achievements); the page does not show `image` / `blurImage` and only the two links use the accent colour. `projectLink` is nullable in both the list item and the case detail: a case without a link is a private project (e.g. a closed corporate admin app), and `ProjectLink` (`shared/ui`, helper `hasProjectLink`) renders the dictionary text `projectPrivate` ("Private project" / "Закрытый проект") instead of an external link in `CaseBlock` and `CaseAbout`; the stub's `nova` case has no link. Nullable `image` / `blurImage` render the dictionary text `noImage` via `ImageWithFallback` (in the list); the case window sits in `CaseWindowSlot` (`views/cases/ui`, hook `useReservedHeight` in `lib`), which reserves the expanded window's height from `lg` up so collapsing it does not re-centre it next to the picture and move its title bar (below `lg` nothing is reserved); the object count in the `RetroWindow` status line is a decorative random three-digit number generated inside the component after mount, not backend data.
- **Stub backend**: `pnpm stub:start` (`scripts/stub-api`, typed fixtures from `Schemas`, on the port of `API_URL`) stands in for the backend where there is none. Playwright starts it on port 3101 and builds the app against it; CI starts it before `build`. Update the fixtures after `api:generate` if the contract changes.
- `src/app/_layout/SiteLayout.tsx` holds site-wide layout composition. Its `body` is `relative`, so a page can anchor a decorative layer to the top of the page behind the site menu (the case page background does this; do not make the layer's parent `relative`).
- **Home animations** (`src/views/home/ui/Coffee.tsx`, `CatPaws.tsx`) use `lottie-react` 3.x: the named `Lottie` export, the animation JSON as `src`, events through `subscriptions`, `lottieRef` typed `LottieHandle` (the 2.x `animationData`, default export, `onComplete` and `LottieRefCurrentProps` no longer exist). The paws go back and forth through `useAlternatingDirection` (`views/home/lib`). `loop` and `autoplay` default to `false` in 3.x, so set them explicitly. Both go through `LazyLottie` (`views/home/ui`, `next/dynamic` with `ssr: false`): the ~90 KB gzip lottie chunk loads after hydration, not in the initial JS of `/`, and its loader checks `matchMedia("(min-width: 64rem)")` (the `lg` breakpoint) once at first render and resolves to an empty component below it, because the scene is `hidden` there and `display: none` would still mount the animations and fetch the chunk on phones (resizing across `lg` later does not start them). In unit tests mock `./LazyLottie` (happy-dom has no canvas; `LazyLottie.test.tsx` resets modules per test because `React.lazy` caches the loader result); real playback is checked in the browser and by `e2e/home-animations.spec.ts`.
- **Entrance animations** use `Reveal` (`shared/ui/reveal`, from `@/shared/ui`), the same `reveal-*` keyframes (`globals.css`, 700 ms) on every page:
  - `direction` (`up`/`down`/`left`/`right`/`fade`), `delay` in ms, and `as` (`"div"` or `"li"`, so a list item itself can animate).
  - `trigger="mount"` (default) is server-rendered and CSS-only and plays on load. The home scene and the site menu use it.
  - `trigger="visible"` renders the client `RevealInView`. It holds the keyframe paused (hidden, with its delay not running) until the block is noticeably in the viewport, or until it receives keyboard focus. `useInViewOnce` uses an `IntersectionObserver` with `rootMargin: "0px"` and thresholds `[0, 0.2]`, fires once, and decides with `isFarEnoughInView`: a fifth of the block is visible, or a quarter of the viewport height for a taller block. Do not use a negative bottom `rootMargin` instead: a short last block can then never start. It plays at once without `IntersectionObserver`.
  - Reduced motion shows every block at once.
  - Cases list: `CaseBlock` slides the picture and the `RetroWindow` in from opposite sides (`views/cases/lib/getCaseBlockReveal`). The first block uses `mount`, the rest `visible`.
  - Case page: the header back link, title and facts use `mount`, staggered 80/160/260 ms; the background only fades. About, Stack, the achievements title and each achievement (`lib/getStaggerDelay`) use `visible`.
  - Never put a translating `Reveal` around `CaseBackground` or its ancestors (the `header`). A `translate` makes the element the containing block of the absolute background and detaches it from the page top; only `direction="fade"` (opacity) may wrap its inner layers.
  - Behaviour is covered by `e2e/cases-animations.spec.ts`.
- **Cursor glow** (`CursorGlow`, `shared/ui/cursor-glow`, from `@/shared/ui`): a blue spot that lags behind the mouse on `/cases`, `/cases/[slug]` and `/contacts` (rendered by `CasesPage`, `CaseDetailPage` and `ContactsPage`, never in `SiteLayout`, so not on the home page).
  - One `position: fixed` decorative layer (`aria-hidden`, `pointer-events-none`, `-z-1`) with one element painted by a pre-built `radial-gradient` (`--background-image-glow-spot`, `--color-glow` in `globals.css`). Never add a blur or SVG filter: movement is `transform` only, written straight to `el.style` by `useCursorGlow` (no custom properties, no `top`/`left`), so it stays on the compositor with no layout or paint.
  - The rAF loop eases over real time (`getGlowStep`: `1 - exp(-dt / GLOW_LAG_MS)`, 220 ms, so the lag is the same on 60 and 120 Hz and the glow trails the cursor a little); it idles once settled; `mousemove`, `resize` and a capture-phase `scroll` listener wake it (page scroll does not bubble). Cleanup removes the listeners and cancels the frame.
  - Rendered only for `(hover: hover) and (pointer: fine)` without `prefers-reduced-motion` (`useGlowEnabled`, `useSyncExternalStore`, server snapshot `false`); otherwise nothing is in the DOM.
  - Optional `boundaryId`: nothing of the glow is drawn over that element. Every frame its bottom edge is measured; the glow centre never rises above it (`getGlowTarget`) and the layer is cut there by a `mask-image` with a soft `GLOW_EDGE_FADE` (100 px) below the edge (`getGlowEdgeMask`), written only when the edge moves. The glow therefore reaches the content right under the element. The case page passes `CASE_HEADER_ID` (`views/case-details/config`), which `CaseHeader` puts on its `<header>`; an id and not a ref, because the page is a Server Component.
  - Covered by `e2e/cursor-glow.spec.ts` (mouse, boundary, no glow on touch or with reduced motion).
- **Contacts page** (`src/views/contacts`, `/ru|en/contacts`): header (`ContactsHeader`, `ContactLinks`: the email on one row and the Telegram and LinkedIn icons below it, white with an accent hover/focus; no phone, WhatsApp or X), info block (`ContactsInfo`, `public/bg-contacts-page.svg`) and the message form (`ContactForm`: name, `MethodSelector` (native radios Telegram/Email, always one selected, Email by default), then exactly one contact field in one slot, the email field or the Telegram number/username field, so switching never changes the form height; the values of both are kept separately and validation checks only the shown one; `FormToast`/`FormNotice`). Contact values and limits are in `config/`, the form is built on React Hook Form with a zod schema written with `zod/mini` (import only `zod/mini`, never `zod`: classic zod adds ~15 KB gzip to the `/contacts` chunks; `model/zodMiniImports.test.ts` enforces it, and mini has no method chaining, so `safeParse(schema, value)` and `z.check(...)` replace `schema.safeParse` and `superRefine`): `model/contactSchema` is the single source of the rules, built only from zod's own checks (`z.trim()`, `z.minLength()`, `z.maxLength()`, `z.email()`, `z.pipe()`) in a `z.discriminatedUnion("method", …)` so only the contact field of the chosen method is checked (messages are the codes `required`/`invalidEmail`/`tooLong`) and of `ContactFormValues`; `lib/useContactForm` is a thin `useForm` + `handleSubmit` + the notice (library defaults: the fields write the values, an invalid field is re-validated while it is edited so its error clears once the value is valid, the values of the hidden contact field are kept) and returns `{ methods, submit, isSent }`; `ContactForm` hands `methods` to a `FormProvider` and its fields read and write the form themselves: `ui/ContactTextField` (`useController`, `maxLength` from `getFieldLimit`, the localized error via `getFieldErrorText` from the `errorTexts` it gets) and `MethodSelector` (`useController` on `method`, clears the contact errors when it changes); there is no "too long" message (the field stops at the limit), `lib/useSuccessNotice` owns the notice timer, (the schema is framework-free so a future server handler can reuse it); all texts live in `pages.contacts` of both dictionaries (`tooLong` contains the `{max}` placeholder). `Input` (single/multiline, label, `aria-invalid`/`aria-describedby`) and `Checkbox` (`type="checkbox"` or `"radio"`) are in `shared/ui`; the field/error colours are the `--color-field*` / `--color-error` tokens in `globals.css`. Layout: stacked below `lg`; from `lg` the form is on the left and the info block on the right. **Submit is a TEMPORARY simulation**: nothing is sent, the hook only clears the fields and shows the "message sent" popup (`FormToast`: a persistent `role="status"` layer portalled to `<body>` and `fixed` in the bottom corner of the viewport (bottom right from `sm`, never over the site menu), no close button, hides itself after `SUCCESS_NOTICE_TIME_MS` with a fade-out (`useExitTransition`, `reveal-out`, `TOAST_EXIT_TIME_MS`); portalled because the form sits in a translating `Reveal`, which would become the containing block of a `fixed` child) (`TODO(contacts-delivery)` in `useContactForm`); replace it with a real delivery channel and delete this note. Covered by `e2e/contacts.spec.ts`.
- **Fonts and images**: `src/app/fonts` holds only what is used: Helvetica Neue 400 and 700 upright (woff2) and `BetterVCR.woff2` (Latin + Cyrillic + punctuation subset made with `pyftsubset`; re-subset from the original TTF if other glyphs are needed). Add a face only when a class actually uses it. Case pictures pass `sizes` (`CASE_IMAGE_SIZES`, `views/cases/config`, must match the widths in `CaseBlock`) so the browser downloads a fitting file; keep it in sync when the widths change. The home scene is `hidden` below `lg`: lazy `next/image` pictures there (painting, table) are not downloaded on phones, but an eager one would be, and `next/image` warns in dev when an LCP picture is lazy. So the shelves (the desktop LCP picture) are `ShelvesImage` (`views/home/ui`), a plain `<picture>` with `<source media="(min-width: 1024px)">` and a 1×1 inline placeholder `<img loading="eager">` (same technique as `DeviceBackgrounds`; `next/image` does not optimize SVG anyway). Covered by `ShelvesImage.test.tsx` and `e2e/home-animations.spec.ts` (no scene SVG request on mobile).
- SVGs imported with the `?svgr` query are converted to React components via `@svgr/webpack` (Turbopack rule in `next.config.ts`). Remote images are only allowed from the S3 storage host `437ae070-24d8-4b42-a1ae-ee5af56b340b.srvstatic.uz`. `RetroWindow`, `ImageWithFallback`, `ProjectLink`, `Reveal`, `CursorGlow`, `Input` and `Checkbox` live in `shared/ui`.

## Keeping docs current

When a change alters the project architecture (layers/slices, `src` structure, routing, i18n, key dependencies, MCP servers, commands, hooks/CI), update `CLAUDE.md` and `README.md` in the same change so they never describe outdated structure.

## Code conventions

- Server Components by default; add `"use client"` only for hooks, browser APIs, events, animations, or client-only libs, and keep it as low in the tree as possible.
- **Prefer the standard solution over custom code.** Before writing a helper, validator, regex, hook or workaround, look for the built-in way, in this order: the platform (native HTML attributes such as `maxLength`, `Intl`, CSS), then the libraries already in `package.json` (read their docs with Context7 first: for example zod already has `z.trim()`, `z.minLength()`, `z.email()` and `z.discriminatedUnion()`, and react-hook-form already writes values, re-validates and clears errors through `useController`/`FormProvider`), and only then a new dependency, if it clearly pays off (state its size cost). Use a library's default behavior instead of re-implementing it. Custom code is fine only when no standard way exists or it would break the specified behavior, and then the code comment or the final answer says why. Aim for the simplest, shortest and most readable result; after the first working version ask "what can I delete?" and remove whatever a standard feature makes unnecessary.
- Strict TypeScript, no `any` (ESLint error); use `import type` for type-only imports. Keep JSX declarative: split large UI blocks into focused components, move non-trivial logic into hooks (`useSomething`) or helpers, and don't mix UI, data fetching and state machines in one component. Follow neighbouring patterns before introducing new abstractions.
- **Components are visually clean.** A component file holds one component and its props type, and its JSX reads declaratively: no inline formatting, derivation or business rules, no module-level helper functions, data tables or second components. Everything else goes to its own file in the matching FSD segment of the slice: helpers to `lib/`, types and view-models to `model/`, constants to `config/`, requests to `api/`, subcomponents to their own files (a folder when they come with helpers, assets or tests). A second component, a helper function, a data type or more than about 100 lines in a component file is the signal to extract. `react/no-multi-comp` warns about several components in one file: fix the warning, do not silence it. Use the `feature-sliced-design` skill for where each file belongs.
- Tailwind: use `clsx` for conditional classes; never build class names from dynamic strings (breaks Tailwind/Prettier analysis). Keep the existing pixel/retro visual style.
- Accessibility: interactive elements need an accessible name; images get meaningful `alt` from the dictionary, decorative ones are explicitly decorative.
- Page metadata is created through the existing i18n helpers.

## Testing

- **Every new feature, behavior change and bug fix must ship with tests in the same change; never finish a task without them.** Work test-first (TDD: red → green → refactor): write the failing test, see it fail for the right reason, then implement. New functionality: cover logic with Vitest units and user-visible behavior (routes, redirects, navigation, keyboard flows) with Playwright E2E. Bug fix: write a failing regression test first. Cover both locales (`ru`, `en`) when text, paths or metadata are involved.
- Use the `writing-tests` skill for where tests live, which level to pick, ready patterns and known pitfalls (e.g. `userEvent` hangs under fake timers: use `fireEvent`).
- If something cannot be tested, say what and why in the final answer.

## Verification

- Before finishing: `pnpm check`, plus `pnpm fsd:check` for architectural changes and `pnpm test:e2e` for routing, `proxy.ts`, navigation or UI-flow changes. If a check cannot run, say why. In the final answer list changed areas, the tests you added, and check results.
- **Any UI/UX change must be made using the `ui-ux-pro-max` skill** (invoke it before designing or editing components, layout, styles, interactions or accessibility).
- **Every UI change must be followed by a UI/UX check via the Playwright MCP** (never skip it, even for small tweaks).
- For UI work, verify with Playwright/Chrome DevTools MCP on desktop and mobile viewports: no clipped/overlapping text, focus/hover/active states, no console errors. Use Figma MCP when given a design (treat it as a reference, adapt to FSD, local components, Tailwind and i18n); use Context7 for library docs (`resolve-library-id` first, then `query-docs`); use Next DevTools MCP (`.mcp.json`, versions pinned) to diagnose the running dev server.
